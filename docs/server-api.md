# HTTP API сервера qWDTT

В документе описаны HTTP-интерфейсы серверного бинарника `wdtt-server`. Это API управления профилями и паролями; транспорт туннеля DTLS/WireGuard не является REST API и здесь не рассматривается.

## Слушатели

| API | Протокол | Адрес по умолчанию | Включение |
| --- | --- | --- | --- |
| API устройств профиля | HTTP | `0.0.0.0:56000` TCP | Запускается на адресе `-listen` |
| Административный API | HTTPS | Не запущен | Укажите `-admin-listen`, `-admin-token-file`, `-admin-cert` и `-admin-key` |

Порт `-listen` также используется DTLS через UDP; HTTP API профиля использует TCP на том же номере порта. В стандартной установке административный API доступен на `56002/tcp`. Адрес административного слушателя задаётся явно, например `-admin-listen 0.0.0.0:56002`.

При включении административного API сервер загружает токен из `-admin-token-file` и TLS-сертификат с ключом из `-admin-cert` и `-admin-key`. Если файл токена пуст или недоступен либо сертификат/ключ не заданы, процесс завершает работу с ошибкой. Минимальная версия TLS — 1.2. В приложении сертификат административного API проверяется по сохранённому SHA-256 fingerprint; не отключайте проверку сертификата в собственных интеграциях.

### Развёртывание нескольких нод

Для общего состояния задайте `-database-url` или переменную окружения `WDTT_DATABASE_URL` с PostgreSQL DSN; автоматические таблицы создаются при старте. Без DSN используется локальный JSON-файл и кластерный режим выключен. Каждой реплике задайте уникальный `-node-id`/`WDTT_NODE_ID`; по умолчанию используется hostname. Все ноды должны использовать одну БД, одинаковые owner/admin credentials и одну версию схемы/бинарника. Если в общей таблице ещё нет state, первая нода импортирует в неё существующий локальный `passwords.json`; последующие ноды читают уже общую запись. После перехода используйте PostgreSQL как источник истины и не редактируйте локальные JSON-файлы. Telegram long polling в cluster mode по умолчанию выключен. Если бот нужен, задайте `-bot-node-id`/`WDTT_BOT_NODE_ID`, совпадающий с `node-id`, ровно на одной ноде; токен бота и admin ID настройте только на ней.

Пример запуска одной ноды:

```sh
export WDTT_DATABASE_URL='postgres://wdtt:REDACTED@postgres.internal:5432/wdtt?sslmode=verify-full'
export WDTT_NODE_ID='vpn-node-a'
./wdtt-server -listen 0.0.0.0:56000 -admin-listen 0.0.0.0:56002 \
  -admin-token-file /etc/wdtt/admin.token \
  -admin-cert /etc/wdtt/admin.crt -admin-key /etc/wdtt/admin.key \
  -config-dir /etc/wdtt
```

Для следующей ноды используйте тот же DSN и другой `WDTT_NODE_ID`. Дайте DB-user права на создание таблиц/индексов при первом старте либо создайте схему заранее. PostgreSQL должен быть доступен только серверам приложения/администраторам; используйте TLS с проверкой сертификата, резервное копирование и мониторинг самой БД. Не помещайте production пароль БД в shell history или логи.

Load balancer должен проверять `GET /healthz` каждой ноды на HTTPS admin listener и выводить её из rotation при `503`. Внешний UDP-трафик DTLS/обфусцированных туннелей должен сохранять affinity одного UDP flow к одной ноде: внутренняя сессия и NAT state не переносятся между серверами. Общая БД синхронизирует credentials, device slots, настройки, challenge nonce и online counts, но не проксирует уже установленные туннельные соединения. Для admin HTTPS используйте одинаковый сертификат и ключ на нодах за общим hostname либо TLS termination на ingress с корректной проверкой backend; иначе certificate pinning Android-клиента может отвергать ноду с другим сертификатом.

Оба HTTP-сервера ограничивают тело запроса размером 64 КиБ, заголовки — 16 КиБ; тайм-ауты чтения и записи — 10 секунд, чтения заголовков — 5 секунд.

## Административный API

Все адреса ниже относительные. Базовый адрес имеет вид `https://<host>:<admin-port>`. Успешные ответы и ошибки возвращаются в JSON. Для защищённых запросов передавайте заголовок:

Откройте `https://<host>:<admin-port>/` для встроенной панели управления. При первом входе вставьте admin token; панель хранит его только в `sessionStorage` текущей вкладки и вызывает API на том же origin.

```http
Authorization: Bearer <admin-token>
```

Тело POST-запросов — `application/x-www-form-urlencoded`. Значения токена и пароля не следует помещать в публичные логи или передавать через незашифрованное соединение.

### `GET /healthz`

Проверка готовности конкретной ноды для балансировщика. Не требует Bearer-токена. Возвращает `200` и `{"status":"ready"}`, если запущен userspace WireGuard, загружен хотя бы один WRAP-ключ и (в PostgreSQL mode) БД отвечает на ping; иначе `503` и `{"status":"not ready"}`. Endpoint доступен только на HTTPS admin listener.

### `GET /metrics`

Prometheus exposition format версии 0.0.4. Требует административный Bearer-токен. Содержит gauges/counters для активных соединений, трафика, числа ключей/устройств, WRAP keys, незавершённых challenge, отказов rate limit, ошибок challenge store, uptime и PostgreSQL pool saturation. Трафик, uptime, активные соединения и pool — локальные для процесса; ключи/устройства/challenges используют общее состояние в PostgreSQL mode. При scrape каждой ноды добавьте её адрес/имя как отдельную Prometheus target label.

### `POST /admin/qrcode`

Форма: `payload` — текст до 3000 байт. Возвращает `image/png` с QR-кодом. Требует admin Bearer token; содержимое передаётся в HTTPS POST body, не помещайте profile password в URL. Панель отправляет сюда созданную `qwdtt://config?...` ссылку; QR генерируется локально, без внешнего QR-сервиса.

### `GET /admin/public-address`

Возвращает внешний IPv4 или IPv6-адрес текущего сервера через HTTPS-запрос к сервису определения IP. Требует admin Bearer token. Панель использует endpoint для кнопки автоопределения адреса, который затем попадает в `peer` быстрых ссылок и QR-кодов. Если сервер находится за NAT, балансировщиком или reverse proxy, укажите доступный клиентам адрес вручную.

### `GET /admin/passwords`

Возвращает все сохранённые пароли, включая деактивированные. Истёкшие записи могут быть удалены во время запроса. Порядок элементов не определён.

Ответ `200 OK`:

```json
{
  "passwords": [
    {
      "password": "<credential>",
      "label": "Рабочий телефон",
      "vk_hash": "<vk-call-hash>",
      "ports": "",
      "max_devices": 2,
      "device_ids": ["<device-id>"],
      "expires_at": 1790899200,
      "is_deactivated": false,
      "down_bytes": 1048576,
      "up_bytes": 524288,
      "active_devices": 1
    }
  ]
}
```

`expires_at` — Unix timestamp в секундах UTC; `down_bytes` и `up_bytes` — счётчики байтов; `active_devices` — число подключённых устройств среди привязанных к этой записи. `device_ids` всегда выдаётся массивом; устаревшая запись с одним устройством преобразуется в массив из одного элемента. Если сохранённый лимит устройств не задан, в API показывается `1`. Поле `ports` возвращается как сохранённая строка.

### `POST /admin/passwords`

Создаёт новый пароль доступа. Обязательное поле: `vk_hash` (непустая строка).
Для интеграций с оплатой рекомендуется передавать уникальный `Idempotency-Key` длиной не более 200 байт (например, ID заказа). Повтор с тем же ключом и теми же параметрами в течение 7 дней возвращает исходную запись и пароль; тот же ключ с другим содержимым даёт `409 Conflict`. После удаления или истечения созданного пароля повторный запрос с таким ключом также даёт `409`, а не создаёт новый пароль. Без заголовка поведение остаётся совместимым со старыми клиентами, но автоматической защиты от повторного создания нет.

| Поле формы | Обязательное | Правило / значение по умолчанию |
| --- | --- | --- |
| `vk_hash` | Да | Непустой хеш звонка VK |
| `days` | Нет | `30`; целое число от 1 до 365 |
| `max_devices` | Нет | `1`; положительное целое число |
| `traffic_limit_bytes` | Нет | Лимит суммарного трафика в байтах; `0` или отсутствие поля означает отсутствие лимита. |
| `ports` | Нет | Три числовых порта через запятую: DTLS сервера, WireGuard и локальный порт приложения; например `56000,56001,9000`. Это не список режимов подключения: значения используются при генерации ссылок (`qwdtt://` использует DTLS и локальный порт, legacy `wdtt://` — все три). Пусто означает стандартные значения. |
| `label` | Нет | Если пусто, сервер назначает имя вида `Доступ N` |

Ответ `200 OK` — объект созданного пароля в том же формате, что и элемент `passwords` в списке. Фиксированного программного лимита на количество паролей нет; фактические пределы определяются ресурсами сервера и объёмом базы. Ответ списка содержит все записи.

Пример:

```sh
curl --fail-with-body --cacert ./admin.crt \
  -H "Authorization: Bearer $WDTT_ADMIN_TOKEN" \
  -H "Idempotency-Key: order-2026-000123" \
  --data-urlencode 'vk_hash=<vk-call-hash>' \
  --data-urlencode 'days=30' \
  --data-urlencode 'max_devices=2' \
  --data-urlencode 'label=Рабочий телефон' \
  https://vpn.example.org:56002/admin/passwords
```

Если сертификат выпущен публично доверенным центром, вместо `--cacert ./admin.crt` используйте обычную системную проверку сертификата и не добавляйте `-k`/`--insecure`.

### `POST /admin/passwords/update`

Изменяет существующую запись. Обязательное поле — `password`. Остальные поля необязательны; меняются только переданные поля.

| Поле формы | Правило |
| --- | --- |
| `password` | Искомый пароль, обязателен |
| `label` | Новая метка; пустая строка допустима |
| `vk_hash` | Новый непустой хеш |
| `max_devices` | Положительное целое число |
| `days` | Целое число от 1 до 365; срок пересчитывается от текущего времени |
| `traffic_limit_bytes` | Неотрицательное целое число; `0` снимает лимит |

Ответ `200 OK` — обновлённый объект записи. Неизвестный пароль даёт `404 Not Found`.

### `POST /admin/passwords/reset-traffic`

Сбрасывает входящий и исходящий счётчики указанного ключа и его устройств. Форма: `password`. Активные соединения не прерываются; после сброса их дальнейший трафик учитывается заново.

### `/admin/vk-hash-library`

Общая библиотека рабочих VK-хешей, доступная только с admin Bearer token.

- `GET` возвращает `{ "hashes": [...] }`;
- `POST` принимает form-поле `hashes`: можно вставить обычный текст с `https://vk.com/call/join/<hash>` или `https://vk.ru/call/join/<hash>` ссылками, и endpoint извлечёт из него только хеши; голые хеши также принимаются через запятые, пробелы или строки. Добавляются только уникальные значения;
- `DELETE` очищает библиотеку.

Встроенная панель позволяет выбрать случайные уникальные хеши из библиотеки при создании или изменении ключа. Выбор сохраняется в обычном поле `vk_hash` через запятую и совместим с текущим Android-клиентом.

### `POST /admin/vk-hash-library/check`

Проверяет все хеши библиотеки через VK API. Необязательное form-поле `proxy_url` задаёт полный адрес `socks5://`, `socks5h://`, `http://` или `https://` прокси. Если поле пустое или отсутствует, сервер подключается к VK напрямую. Возвращает результаты с полями `hash`, `working` и `reason`.

### `POST /admin/vk-hash-library/remove-non-working`

Выполняет такую же проверку напрямую или через необязательный `proxy_url`, удаляет из библиотеки все хеши с `working: false` и возвращает число удалённых значений, обновлённую библиотеку и результаты проверки.

### `POST /admin/passwords/deactivate`

Форма: `password`.

Деактивирует пароль, закрывает его активные соединения и отключает привязанные WireGuard-устройства. Запись остаётся в базе. Ответ `200 OK` — объект записи с `is_deactivated: true`.

### `POST /admin/passwords/activate`

Форма: `password`.

Повторно включает сохранённый пароль. Ответ `200 OK` — объект записи с `is_deactivated: false`. Если не удалось зарегистрировать ключ WRAP, сервер возвращает `500 Internal Server Error`.

### `POST /admin/passwords/unbind-device`

Форма: обязательное `password`, `device_id` необязателен. Непустой ID отвязывает одно устройство; пустой ID отвязывает все устройства.

Отвязывает указанное устройство, отключает соответствующий WireGuard peer и освобождает слот устройства; сам пароль не удаляется. Если `device_id` пустой, отвязывает все устройства этого ключа. Ответ `200 OK` — обновлённый объект записи.

### `POST /admin/passwords/delete`

Форма: `password`.

Удаляет пароль, связанные с ним устройства и активные соединения. Операция необратима. Ответ `200 OK`:

```json
{"success": true}
```

Для административных POST-запросов, кроме `/admin/passwords`, сервер принимает только `POST`; неверный метод даёт `405 Method Not Allowed`. `OPTIONS` возвращает `200` и перечисляет разрешённые методы и заголовки `Authorization`, `Content-Type` и `Idempotency-Key`. Сервер не задаёт `Access-Control-Allow-Origin`, поэтому эти заголовки сами по себе не разрешают браузерный запрос с другого origin. Preflight не отменяет Bearer-авторизацию реальных запросов.

## API устройства профиля

Базовый адрес имеет вид `http://<host>:<listen-port>`. Эти маршруты не принимают административный Bearer-токен. Для каждого защищённого действия клиент сначала получает одноразовый nonce, затем доказывает знание пароля профиля с помощью HMAC-SHA-256. Сам пароль в HTTP-форму не отправляется.

### `POST /api/profile/challenge`

Тело пустое. Ответ `200 OK`:

```json
{"nonce": "<base64url-random-value>"}
```

Nonce действителен одну минуту и может быть использован только один раз при успешной проверке подписи. Для одного IP действует token bucket: до 1000 запросов burst и пополнение со скоростью 250 запросов в секунду. В PostgreSQL mode бакет общий для всех нод. Такой burst рассчитан на клиентов за общим NAT; лимитер использует адрес TCP-пира и намеренно не доверяет `X-Forwarded-For`. Одновременно хранится не более 32768 nonce, устаревшие записи очищаются фоново примерно каждые 15 секунд. Превышение скорости, ёмкости хранилища или лимита состояний IP возвращает `429 Too Many Requests`; при недоступности общей БД endpoint возвращает `503 Service Unavailable`.

### `POST /api/profile/status`

Тело — `application/x-www-form-urlencoded` с полями `device_id`, `nonce`, `key_id` и `proof`, вычисленными для действия `status` (см. раздел «Подпись profile-запроса»).

Ответ `200 OK`:

```json
{
  "max_devices": 2,
  "bound_devices": 1,
  "active_devices": 1,
  "is_current_bound": true,
  "expires_at": 1790899200
}
```

### `POST /api/profile/unbind`

Тело такое же, но подпись вычисляется для действия `unbind`. Непустой `device_id` отвязывает только это устройство. Пустой `device_id` отвязывает все устройства ключа, освобождает их слоты и отключает соединения; это значение подписывается как пустая строка.

Ответ `200 OK`:

```json
{"success": true}
```

### Подпись profile-запроса

Значения кодируются как поля формы UTF-8 (`application/x-www-form-urlencoded`). Для каждого действия запрашивайте новый nonce. Порядок вычислений и точные байты:

1. `key_id` — нижний hex от `SHA-256("WDTT-PROFILE-ID-v1" || 0x00 || password)`.
2. `proof` — нижний hex от `HMAC-SHA-256(key=password, message=action || "\n" || device_id || "\n" || nonce)`.
3. Отправьте `device_id`, `nonce`, `key_id` и `proof` в теле формы. `action` равен ровно `status` или `unbind` и не передаётся отдельным полем.

Минимальный пример на Python 3 со стандартной библиотекой:

```python
import hashlib
import hmac
import json
import urllib.parse
import urllib.request

base = "http://vpn.example.org:56000"
password = "<profile-password>"
device_id = "<device-id>"
action = "status"  # Для отвязки укажите "unbind".

with urllib.request.urlopen(
    urllib.request.Request(base + "/api/profile/challenge", data=b"")
) as response:
    nonce = json.load(response)["nonce"]

key_id = hashlib.sha256(
    b"WDTT-PROFILE-ID-v1\0" + password.encode("utf-8")
).hexdigest()
message = f"{action}\n{device_id}\n{nonce}".encode("utf-8")
proof = hmac.new(password.encode("utf-8"), message, hashlib.sha256).hexdigest()
body = urllib.parse.urlencode({
    "device_id": device_id,
    "nonce": nonce,
    "key_id": key_id,
    "proof": proof,
}).encode("ascii")

request = urllib.request.Request(
    base + "/api/profile/" + action,
    data=body,
    headers={"Content-Type": "application/x-www-form-urlencoded"},
)
with urllib.request.urlopen(request) as response:
    print(response.read().decode("utf-8"))
```

Этот HTTP-интерфейс не использует TLS. HMAC защищает пароль от передачи в открытом виде и запросы — от повторного использования после успешной проверки nonce, но не шифрует соединение и не защищает от перехвата/подмены трафика. Используйте доверенную сеть или TLS-терминацию перед сервером, если API доступен через недоверенную сеть.

## Авторизация и коды ошибок

Административная авторизация сравнивает SHA-256 переданного Bearer-токена с хешем токена из файла. После пяти неудачных попыток с IP-адреса за минуту новые попытки этого адреса блокируются на пять минут. Успешная авторизация сбрасывает счётчик.

| HTTP-код | Значение |
| --- | --- |
| `200` | Запрос успешно обработан |
| `400` | Отсутствующее или некорректное поле формы |
| `401` | Нет/неверный Bearer-токен либо профиль не прошёл проверку |
| `404` | Административный запрос ссылается на неизвестный пароль |
| `409` | Idempotency-Key повторно использован с другим запросом или его созданный пароль уже удалён/истёк |
| `405` | Метод не поддерживается маршрутом |
| `429` | Превышен лимит запросов challenge |
| `503` | Общая PostgreSQL/challenge/status служба недоступна |
| `500` | Внутренняя ошибка генерации/регистрации ключа, nonce или сохранения изменений |

Административные ошибки имеют JSON-форму `{"error":"..."}`. Для ошибок API профиля сервер формирует тело вида `{"error":"..."}` через `http.Error`; ориентируйтесь прежде всего на HTTP-код, так как `Content-Type` ошибки может быть `text/plain`.

## Ограничения и примечания

- В API нет маршрута health check; неизвестный путь возвращает стандартный `404` HTTP-сервера.
- `OPTIONS` административных маршрутов служит только для CORS preflight и не проверяет Bearer-токен.
- Счётчики трафика и состояния устройств относятся к внутренней базе сервера; API не предоставляет отдельные методы для произвольного изменения счётчиков.
- Поле `ports` передаётся и возвращается как строка; данный HTTP-обработчик не разбирает и не валидирует её формат.
- В PostgreSQL mode password/device state хранится одним JSONB snapshot и защищён PostgreSQL advisory lock: проверка и резервирование device slots сериализуются между нодами, а изменение версии подтягивает credentials и peers на остальные ноды примерно за 250 мс. Challenge одноразовые и per-IP rate bucket общие; active-device presence хранится как lease и исчезает после потери heartbeat. Это рассчитано на небольшой кластер для вашего масштаба, но JSONB snapshot и общий lock остаются точкой сериализации. Для существенно более высокого write throughput следующий шаг — нормализовать passwords/devices/idempotency в отдельные таблицы и использовать транзакционные row locks.
